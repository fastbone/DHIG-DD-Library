Getting the credentials for a SharePoint Online library

DD Library signs in to SharePoint as itself, not as you — so it needs its own identity in Microsoft Entra ID. This walks through creating that identity and collecting the values the Connect a library form asks for. Once per tenant, then one grant per library.

What you need, and who can do it

Four values come out of this, and the form needs all four. Read them first — knowing what you are collecting makes the clicking obvious.

The four values

Site URL
You already have this — the address of the SharePoint site, copied from your browser.
Directory (tenant) ID
A GUID identifying your organisation. From the app's Overview page (step 2).
Application (client) ID
A GUID identifying the app you are about to create. Same page (step 2).
Client secret
The app's password. Shown exactly once, at the moment you create it (step 3).

There is a fifth thing that is not a value but a permission grant — step 6. It is the step people miss, and skipping it produces an access denied that looks like wrong credentials.

Who has to do it

  • Registering the app (steps 1–4) — any user can, in most tenants. Some restrict it to the Application Developer role.
  • Granting admin consent (step 5) — a Global Administrator, Privileged Role Administrator, or Cloud Application Administrator. There is no way around this; it is one button, so it is a small ask.
  • Granting access to the library (step 6) — a SharePoint administrator.

If that is not you, parts 1–3 can be handed over whole. Whoever does them needs to send back only the three values.

Send the secret carefully

The client secret is a password to the library's contents. Send it through a password manager or a secret-sharing link, not email or chat. Once it is in DD Library it is encrypted at rest and never shown again.

Part 1 — Register the app

Everything here happens in the Microsoft Entra admin center at entra.microsoft.com. The same pages exist in the Azure portal under Microsoft Entra ID, if that is where you normally work.

1

Create the registration

Go to Identity → Applications → App registrations, then New registration.

  • Name — something recognisable in an audit log a year from now. DD Library corpus sync works.
  • Supported account types — Accounts in this organizational directory only (single tenant).
  • Redirect URI — leave it empty. Nobody signs in to this app interactively, so it needs no redirect.

Then Register.

2

Copy the two IDs

You land on the app's Overview page. Two of the four values are right there, under Essentials:

  • Application (client) ID
  • Directory (tenant) ID

Both are GUIDs and look alike — 3fa85f64-5717-4562-b3fc-2c963f66afa6. Label them as you paste them somewhere, because swapping the two produces a login error that names neither.

3

Create the client secret

Left menu → Certificates & secrets → Client secrets tab → New client secret.

  • Description — DD Library plus the month, so the next person knows which is which.
  • Expires — 12 or 24 months. 24 is the maximum Entra allows; the sync stops working the day it lapses, so see Before it expires.

Then Add.

Copy it now

The table shows two columns. You want Value — the long string, not the shorter Secret ID beside it. The Value is displayed only until you navigate away; after that it is masked forever and the only fix is deleting the secret and making another.

Pasting the Secret ID by mistake is the most common failure here. It is a GUID; a real secret is longer and mixes case and punctuation, something like zXt8Q~kA3v.Lm9_qR2sT7uV1wXyZ4aB6cD8eF0g.

Part 2 — Give it permission to read SharePoint

4

Add Sites.Selected as an application permission

Left menu → API permissions → Add a permission → Microsoft Graph.

Now the fork that matters: choose Application permissions, not Delegated permissions. Delegated permissions act on behalf of a signed-in user, and no user ever signs in here — pick that and the sync fails with a permission error no matter what else you do.

Search for Sites.Selected, tick it, and Add permissions.

Why this one

Sites.Selected grants nothing on its own. Access has to be handed to the app site by site, which is step 6 — so the blast radius of this credential is exactly the libraries you choose. Sites.Read.All would also work and needs no step 6, but it grants read access to every site in the tenant. For a due-diligence tool holding one deal's data room, that is the wrong trade.

5

Grant admin consent

Adding the permission only requests it. On the same API permissions page, click Grant admin consent for <your organisation> and confirm.

The Status column must end up reading Granted for <your organisation> with a green tick. If it still says Not granted, this step did not happen — that is what to check first when the connection test fails.

Part 3 — Grant the app access to the one library

This is the step with no button in the portal. It is one command, run by a SharePoint administrator, and either route below does the same thing. Pick whichever your admin already has to hand.

6

Route A — PnP PowerShell

The shorter route if PowerShell is already in use for SharePoint admin.

PowerShell

Install-Module PnP.PowerShell -Scope CurrentUser

Connect-PnPOnline -Url "https://contoso.sharepoint.com/sites/ProjectKestrel" -Interactive

Grant-PnPAzureADAppSitePermission `
  -AppId       "<Application (client) ID>" `
  -DisplayName "DD Library corpus sync" `
  -Permissions Read

Replace the URL with your site and the app id with the one from step 2. Read is deliberate — DD Library only ever reads, and a write grant would let a misconfiguration change the data room.

If the sign-in complains

Recent PnP versions ask for your own client id for interactive sign-in rather than using a shared one. If Connect-PnPOnline -Interactive errors about a missing client id, run Register-PnPEntraIDAppForInteractiveLogin once as the message directs, then repeat the connect. That is PnP's own registration and has nothing to do with the app you just made.

Route B — Graph Explorer

No installation. Open developer.microsoft.com/graph/graph-explorer, sign in as an administrator, and consent to Sites.FullControl.All when it asks — that is Graph Explorer's own permission for making the grant, not something added to your app.

First, get the site's ID. Split your site URL into the hostname and the path after it:

GET

https://graph.microsoft.com/v1.0/sites/contoso.sharepoint.com:/sites/ProjectKestrel

Copy the id from the response. It is a compound value with two commas in it — contoso.sharepoint.com,8a7b…,4c2d… — and you need the whole thing.

Then grant read access, pasting that id into the URL:

POST

https://graph.microsoft.com/v1.0/sites/<the id you just copied>/permissions

Request body

{
  "roles": ["read"],
  "grantedToIdentities": [
    {
      "application": {
        "id": "<Application (client) ID>",
        "displayName": "DD Library corpus sync"
      }
    }
  ]
}

A 201 Created response means the app can now read that site, and only that site.

Part 4 — Enter it in DD Library

7

Connect the library

Back in the app: Corpus tab, then SharePoint libraries → Connect a library…

FieldWhat goes in it
Name Anything you will recognise. It labels the mirror folder on disk.
Site URL As copied from the browser. A URL pointing at a folder inside the library is fine — the site part is what gets used.
Library Leave blank unless the site has several document libraries. Blank takes the default one, usually Documents.
Directory (tenant) IDFrom step 2.
Application (client) IDFrom step 2.
Client secretThe Value from step 3.
Sync automatically Start on manually only. Set an interval once a first sync has worked.

Saving tests the connection immediately, so a wrong secret or a missing site grant is reported there and then rather than at the first sync. Then use test on the row, and only after that sync now.

What a first sync does

It checks the library's size against your disk, fetches only the indexable file types, mirrors the folder tree into the data volume, and then indexes it like any local folder. Deletions are mirrored on later runs, capped so a connection pointed at the wrong library cannot empty the mirror in one go.

If the test fails

The test does two things — fetches a token, then reads the library root — so its message tells you which half broke.

What it saysWhat it means
invalid_client The secret is wrong, expired, or is actually the Secret ID from step 3 rather than the Value. Create a fresh secret and paste the Value.
unauthorized_client
AADSTS700016		 The application ID does not exist in this tenant. Usually the two GUIDs from step 2 have been swapped.
AADSTS900023
tenant not found		 The directory (tenant) ID is wrong — the other half of the same swap.
access denied · 403 The credentials are fine and the app has no rights to this site. Either admin consent (step 5) was never clicked, or the per-site grant (step 6) was not done — or was done against a different site.
site not found · 404 The site URL does not resolve. Paste it again straight from the browser; check for a trailing path from a different site collection.
no document library The Library name does not match anything on the site. Clear the field to take the default.
timeout · connection refused Not a credentials problem. The server cannot reach login.microsoftonline.com, graph.microsoft.com or *.sharepoint.com. Check egress from the Docker host.
rclone not installed The sync engine is missing from the image. Rebuild it — deploy/update.sh on the host.

Failures also land in the Indexing tab's activity log, where errors only plus copy for a bug report gives you the full response rather than the one-line summary.

If a sync is refused on size

over the N GB limit is DD_MAX_SYNC_GB, and the figure it compares is what this connection would fetch — the indexable types, each under the per-file ceiling — not the library's headline size in SharePoint. needs another N GB is the data volume instead: the mirror is a second full copy of those files, so the volume has to hold them alongside the index.

Raising the limit in .env takes effect when the container is recreated — ./deploy/update.sh on the host, or docker compose up -d — not on docker compose restart, which keeps the old values. ./deploy/update.sh --status says whether what is running matches the file. The up to N GB figure above the connections is the running app's own limit, so compare it with the refusal: the same number means the limit really was reached, a lower one means the new value has not been picked up yet. A stored failure also outlives the config that caused it — check last attempt on the row before acting on the message.

Before it expires

Entra client secrets have a hard maximum lifetime of 24 months, and syncs begin failing with invalid_client the day one lapses — silently, unless someone is watching the log.

Two minutes now saves an afternoon later:

  • Put a calendar reminder a month before the expiry date you chose in step 3.
  • When it fires: create a new secret on the same app registration, paste its Value into edit on the connection, then delete the old secret.

Nothing else needs redoing — the app registration, the consent and the per-site grant all survive a secret rotation. Leaving the secret field blank when editing means keep the current one, so an accidental save cannot wipe it.

One thing to be clear about internally

DD Library authenticates as the app, not as the person asking a question, so SharePoint's own per-user permissions do not carry across. Anything synced is readable by everyone who can sign in to DD Library. Point a connection only at libraries whose whole contents the deal team is meant to see.
